# 首页列表与官方活动同步

活动列表保留全部有效日程，桌面同时可见 4 项（每行 96px），手机最多 4 项（每行 124px）；其余独立滚动。鱼窗默认未来 24 小时，全部匹配条目进入最多四行的滚动窗口。模块的标题、统计与操作区不滚动。活动底部的其余日程/待核实公告按钮已移除，完整日历入口继续保留。

导航分类全部展开，手机换行，不隐藏在更多分类或下拉选择中。

## 官方活动：每 6 小时自动同步或管理员手动同步

- 固定官方源：`https://cqnews.web.sdo.com/api/news/newsList` 和 `newsDetail`，以及校验过的盛趣活动专题。不是第三方活动源。
- 新闻 API 返回公告，不保证结构化活动日期。正文明确开始时间即可显示开始倒计时；结束倒计时和 ICS 仍要求完整起止时间，发布时间不代替活动时间。
- 快照超过 6 小时后，公共 JSON/ICS 请求尝试同步；获准同步的请求等待结果（最多 20 秒），成功后直接返回新快照，避免页面再等 6 小时。并发请求或失败时使用已有快照；没有访问时不运行。
- 全边缘共用现有 D1 原子限流器，专用 `public-calendar:official-refresh:cn` 配额每 6 小时最多一次；不新增数据库迁移或 Cron。
- 管理台「活动内容管理 → 同步官方公告」调用 `POST /api/v1/admin/calendar/refresh`，仅独立 owner 会话可用，每 5 分钟最多一次。跳过自动配额和进程内官方缓存，等待同步完成；失败保留旧快照，人工修改层保持独立。
- 上游请求整体 20 秒预算、单请求 10 秒，响应最多 1MB。没有跨请求复用 I/O Promise。
- 只接受完整、非空、来源正确的新数据，条件 UPSERT 防止较慢结果覆盖更新的快照。失败不删除数据、不修改旧同步时间；人工编辑层仍独立保留。
- 首页首次打开读取一次，之后每 6 小时最多自动请求一次应用接口；返回前台也检查间隔。后台标签暂停轮询，普通刷新按钮只重新读取已保存数据，不能提前触发官方同步。秒级倒计时继续本地计算。刷新失败保留上一份列表并标记缓存状态。
- 这不是官方推送；管理员手动同步后的内容在普通页面下次读取时显示。Cloudflare 到盛趣的网络异常时会继续使用最近快照。

## Worker 请求兼容性

Cloudflare 的生产运行时不支持 Fetch 的 `redirect: 'error'`，会在发送请求之前抛出 TypeError；本机 Node 和被模拟的测试 fetch 没有暴露这一差异。官方 JSON 和专题 HTML 请求现在统一使用 `manual`，并通过 `response.ok` 拒绝 3xx，因此仍不跟随官方跳转或跨域跳转。失败诊断仅包含固定端点类型、HTTP 状态和脱敏的原生错误类型，不记录公告正文、URL 查询、凭证或个人数据。

参考：https://developers.cloudflare.com/workers/runtime-apis/request/#constructor 。
